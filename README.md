# 采购清单

一个自托管的采购清单工具：把采购清单从表格搬进网页 —— 随手改数量、记付款、看进度，局域网内任意设备打开即用，数据存在自己机器的 SQLite 文件里。

它最初是为装修采购写的，所以默认自带一套家装的房间名与分类（都可以改）。现在可以建**多份互相独立的清单**（装修采购、年货采购、项目物料……），换件事用不需要再装一个程序。

**它解决什么**：一次采购要买几十上百种东西、分布在十几个分组里，还得分次付款、随时看"总共多少 / 花了多少 / 还差多少"。用表格维护容易算错、改乱、看不出进度。这里把这些做成结构化数据：

- **物料 × 分组的分配矩阵**：每样东西用在哪里、各几个，一眼看全，某个分组还能单独定价
- **多笔采购记录**：一笔付款可以覆盖多件物料，记录后自动算已付、未付与实付单价，状态自动变成"部分已买 / 已买完"
- **自动汇总看板**：总价、日常价、已付、未付、各分类与各分组的分布、未采购清单

界面为 iOS 毛玻璃风格，需要登录（单账号，首次使用时在页面上创建），SQLite 单文件存储，备份就是拷一个文件。

## 多份清单

- 顶部左上角是**清单切换器**，旁边「+」新建。每份清单有独立的物料、分组、分类，互不影响
- 新建时可以选**空白清单**，也可以**照抄某份现有清单的分组与分类**（只搬结构，不带物料和付款记录）——同一套房做二期、或者新项目沿用同样的分组时省事
- 分组和分类在「设置 / 数据」里按清单维护
- 导入导出都只作用于**当前清单**：导出的 xlsx 文件名带清单名，导入也只改这一份
- 删除清单会连它里面的物料、分组、分类一起删掉，最后一份不允许删除（至少留一份，不然界面没东西可看）
- 浏览器会记住你上次看的是哪份清单，刷新后还在那一份上

## 功能

- **总览看板**：原价合计 / 日常价合计 / 已付 / 未付 四张统计卡，已付卡上另给「实际优惠」「日常价优惠」、未付卡上另给「日常价未付」，把两个口径各自拆成三段（见下方金额口径）；实付构成、分类占比、采购进度三个环形图；分类对比、分组金额分布、**按月已付**（近 6 个月，没付款的月份补 0，另有"未填日期"的钱数提示）三张柱状图；未采购金额 Top 6 与未采购清单（可一键跳到清单页）。整屏自适应，无页面滚动
- **物料清单**：名称 / 品牌 / 型号 / 分类 / 数量 / 单价 / 日常价 / 已付·未付 / 采购状态 / 备注；支持关键词、分类、采购状态（全部 / 未买 / 部分已买 / 已买完）筛选；勾选后可批量删除
- **多笔采购记录**：点采购状态标签打开「记一笔采购」，可逐笔录入实付数量、实付金额与付款日期（统一成 `YYYY-MM-DD`，乱填会被拦下；Excel 里写成真日期的单元格导入时也会自动归一化），自动算实付单价；也支持「按日常价付清」与「清零」（均有二次确认）。已付 = 各笔金额之和，未付 = 剩余数量 × 单价
- **分配矩阵**：物料 × 分组矩阵，点单元格填数量 / 覆盖单价 / 备注；买齐的分组标绿（**只在能确定时标**，见下方说明，宁可不标也不猜）；底部固定合计行（各分组数量 + 总量与金额）
- **数据管理**：导出当前清单为 xlsx（含日常价未付、实际优惠、日常价优惠三列）；按模板导入（覆盖或按名称合并）；整库 `.db` 备份的下载与恢复；分组与分类可增改
- **登录**：单一管理员账号，首次使用时在页面上创建；网页端和安卓 App 共用同一账号

## 快速开始（本地运行）

依赖：Python 3.11+，Node 18+

```bash
python -m venv .venv
.venv\Scripts\pip install -r backend\requirements.txt

# 前端（首次运行或改了前端代码后）
cd frontend && npm install && npm run build && cd ..

# 启动
cd backend && ..\.venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

打开 `http://127.0.0.1:8000`，首次访问会让你创建一个管理员账号（用户名 + 至少 6 位密码），建好就直接进去了。首次启动会自动建库、建默认清单，并写入默认分组与分类。

## 登录与账号

- 只有一个账号，网页端和安卓 App 共用。第一次打开网页时创建，之后可以在「设置 / 数据 → 账号」里改密码。
- 网页端登录态放在 httpOnly Cookie 里，有效期 30 天；安卓端存 token 后每个请求带 `Authorization: Bearer`。
- 改密码会让其它设备上已登录的会话失效，当前这台会自动续上，不用重新登录。
- 连续输错 5 次密码会锁定 1 分钟。
- **忘记了密码**：停容器后用命令行重设，不需要动数据库文件。

  ```bash
  docker compose exec app python scripts/reset_password.py
  # 或者本地运行：
  cd backend && ..\.venv\Scripts\python scripts/reset_password.py
  ```

- ⚠️ **账号创建之前是有一个窗口期的**：那一刻局域网里谁先打开这个页面，谁就能把管理员账号建走。所以部署完建议马上打开页面把账号建好；再稳妥一点就别把这个端口暴露到内网之外。
- 明文 HTTP 下 token 在局域网里是可以被抓包的。这个应用面向的是自己家里的内网，要防住这一点得上 HTTPS（上了 HTTPS 记得把 `RENOVATION_COOKIE_SECURE` 打开）。

Windows 下也可直接双击根目录的 `启动服务.bat`（前台）或 `启动服务-后台运行.bat`。
开发模式（前端改动实时生效）：`cd frontend && npm run dev`（5173 端口，自动代理 `/api` 到 8000）。

> 注意：改**后端**代码需要重启服务才会生效（uvicorn 未开 `--reload`）。

## 升级到多清单版本

从旧版本（只有一份装修采购清单）升上来不用做任何事：**启动时会自动迁移**。

迁移做的事只有三件 —— 建一份名为「采购清单」的默认清单、把现有的物料/分组/分类都归到它名下、重建分类表以支持"不同清单可以有同名分类"。现有数据一条都不会动，老版安卓客户端不带清单标识访问时，看到的也正是这份默认清单，和升级前完全一样。

- **动手前先备份**：库文件会复制成 `renovation.db.bak-<时间戳>`（就在数据目录里），迁移完可以确认没问题再删掉
- **过程会记日志**：升级完 stdout 里有一行 `[升级] 老库已升级为多清单：…`，写明归入了多少条数据、备份文件在哪。容器里 `docker compose logs app | grep 升级` 就能看到
- **全程一个事务**：任何一步失败整体回滚，库仍停在迁移前的样子
- **迁移后自检**：逐表比对迁移前后的行数与内容，条数、数量、金额必须一字不差，否则回滚并报错
- **重复启动不会重复迁移**，也不会重复备份

**万一要回滚**：停掉服务，把 `renovation.db.bak-<时间戳>` 改名回 `renovation.db`（旧的 `renovation.db` 先挪走），再用旧版本的镜像/代码启动即可。备份就是迁移前那份库，不含任何新结构。

## 安卓 App

`android/` 下是同一套数据的原生安卓客户端（Kotlin + Jetpack Compose），功能对齐网页版：总览看板、物料清单（增删改 + 记一笔采购）、分配矩阵（列表 / 矩阵双模式）、**多清单切换与新建（可选空白或照抄某份清单的分组与分类）**、分组与分类管理、Excel 导入导出。登录用的是同一套账号，登录一次后 token 存在本地，之后不用反复输密码。

手机和网页可以同时用，两边看到的是同一份数据（同一个清单）：在手机上记一笔付款，网页刷新就能看到；反过来也一样。**升级时先升服务器再升 app** —— 新后端配老 app 完全可用（老 app 会落到默认清单，看到的就是升级前那份数据），反过来则拿不到清单列表。

**服务器地址可自定义**：首次启动填写后端地址，之后可在「设置」里随时修改，改完立即生效、不用重启。地址规则很宽松 —— 省略 `http://` 和端口都行，默认按 `8000` 处理，输入时界面会实时回显最终连接的地址（如「将连接到 `http://192.168.1.9:8000`」）。连接失败时会明确显示连的是哪个地址，并提供「重试」与「修改地址」。

### 构建

```bash
cd android
./gradlew assembleDebug      # app/build/outputs/apk/debug/app-debug.apk
./gradlew assembleRelease    # 经 R8 压缩，约 1.9MB
```

需要 JDK 17 与 Android SDK（platform 35 / build-tools 35）。SDK 路径写在 `android/local.properties`（该文件不入库）；依赖仓库配置了阿里云镜像，国内网络可直接构建。

### 安装与使用

把 APK 传到手机点击安装即可（debug 与 release 都使用 debug 签名，个人自用足够）。手机需与后端在同一个局域网。模拟器里调试宿主机上的后端，地址填 `10.0.2.2:8000`。

界面是深色玻璃拟态 + 霓虹蓝配色，视觉规范见 [`android/DESIGN.md`](android/DESIGN.md)。

也可以由 GitHub Actions 自动构建：`.github/workflows/android.yml` 在 `android/` 有改动时产出 APK artifact。

## Docker 部署

镜像由 GitHub Actions 构建并推送到 GitHub Container Registry，`main` 分支每次推送自动更新：

```
ghcr.io/xiaoyuan0218/renovation-procurement:latest     # 最新
ghcr.io/xiaoyuan0218/renovation-procurement:sha-xxxxxx # 按提交回滚
```

服务器上只需要一个 compose 文件（仓库根目录的 `docker-compose.yml`，镜像地址已填好）：

```yaml
services:
  app:
    image: ghcr.io/xiaoyuan0218/renovation-procurement:latest
    container_name: renovation-procurement
    restart: unless-stopped
    ports: ["8000:8000"]
    volumes: ["./data:/data"]        # 数据库落在宿主机，备份拷这个目录
    environment:
      TZ: Asia/Shanghai
      RENOVATION_DATA_DIR: /data
```

```bash
mkdir -p /opt/renovation-procurement && cd /opt/renovation-procurement
# 保存上面的 docker-compose.yml

# 镜像包若为私有：先登录一次（PAT 勾选 read:packages）；设为 Public 则免登录
echo "<你的PAT>" | docker login ghcr.io -u xiaoyuan0218 --password-stdin

docker compose up -d                          # 启动并拉取镜像
docker compose logs -f app                    # 查看日志
docker compose pull && docker compose up -d   # 更新到最新构建
```

打开 `http://<服务器IP>:8000`，第一次会提示创建管理员账号 —— 部署完建议立刻建好，见上面「登录与账号」里提到的窗口期。镜像内已含构建好的前端与后端，服务器无需安装 Node/Python。

**不用 CI、本机构建**：`docker build -t renovation-procurement .`，把 compose 的 `image:` 换成 `renovation-procurement:latest` 即可。

## 配置

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `RENOVATION_DB` | `<项目>/data/renovation.db` | SQLite 文件完整路径 |
| `RENOVATION_DATA_DIR` | `<项目>/data` | 数据目录（签名密钥也放这里） |
| `RENOVATION_DIST` | `<项目>/frontend/dist` | 前端静态文件目录 |
| `RENOVATION_SECRET` | 自动生成 | 登录 token 的签名密钥。不设就在数据目录生成 `.secret_key` 并一直用下去；**改这个值等于让所有设备登出** |
| `RENOVATION_COOKIE_SECURE` | `false` | 只在 HTTPS 下才该设为 `true`。局域网走明文 HTTP 时设成 true，浏览器会直接丢弃登录 Cookie，症状是"登录成功但下个请求又是未登录" |
| `RENOVATION_SESSION_DAYS` | `30` | 登录状态保留天数 |

端口由启动命令的 `--port` 决定（compose 里映射 8000）。容器内数据目录固定挂 `/data`。

## 备份与恢复

两种备份各管一段，日常用 xlsx，搬家/换机器用 `.db`：

- **导出当前清单（xlsx）**：只含**当前清单**的物料、分配与采购记录，适合存档、发给别人、或者在另一份清单里导入
- **下载整库备份（.db）**：整个数据库文件的一致性快照，含所有清单、账号、登录密钥。想换台机器跑，把这份文件放到新机器的数据目录改名成 `renovation.db` 即可
- **从 .db 备份恢复**：会用备份里的内容**整体替换**当前数据（连账号一起）。恢复前会自动把当前库另存一份 `renovation.db.bak-<时间戳>`，所以传错文件也救得回来。恢复的是老版本备份也没关系，会顺带自动升级结构。备份来自另一台设备时，恢复后需要用那份备份里的账号重新登录

> 打算直接换文件的话（而不是用页面上的恢复），记得先停服务再动，两个进程同时写同一个 SQLite 文件是要坏的。

## Excel 导入 / 导出

- **导出**：一键导出当前清单为 xlsx，含「物料汇总 / 布点明细 / 采购记录」三个 sheet，可再次导入。物料汇总里除「未付数量 / 未付金额」外，还导出「日常价未付 / 实际优惠 / 日常价优惠」三列（口径见上方「金额口径」）；这三列是算出来的，导入时忽略。三个 sheet 都带「物料ID」列，用来区分同名物料，导入时优先按它匹配、留空则按名称
- **按模板导入**：下载模板填写后导入，支持「覆盖当前清单」与「按名称合并」两种模式；导入只影响当前清单
- **从历史表格预置**：如果已有一份"产品×房间布点 + 物料汇总 + 类目汇总"分区的表格，可用
  `backend/scripts/seed_from_excel.py` 一次性导入（解析分组分配与分组单独价、把"实付"折算成采购记录，并以表内合计行校验金额口径）：

  ```bash
  cd backend && ..\.venv\Scripts\python scripts/seed_from_excel.py <你的表格.xlsx>
  ```

- **差异核对**：`backend/scripts/compare_with_excel.py` 会把 Excel 与当前数据库逐项配对，
  输出数量 / 单价 / 已付 / 分配的差异清单与汇总差额，方便确认手工录入是否与表格一致

## 测试与回归脚本

```bash
cd backend && ..\.venv\Scripts\python -m pytest tests -q      # 单测：金额口径 / 删除级联 / 多清单隔离 / 老库迁移 / 备份恢复 / 导入导出 / 登录鉴权

# 以下需要先启动服务（默认 127.0.0.1:8000，可用 WALKTHROUGH_BASE 指向其他实例）
.venv\Scripts\python backend\scripts\walkthrough.py           # 功能走查：登录页、看板数字、矩阵编辑、导入导出
.venv\Scripts\python backend\scripts\measure_layout.py        # 布局回归：无整页滚动、表格撑满、图表填充
```

走查脚本会在开头和结尾各取一次**全库快照**（逐物料的金额口径 + 分配/记录明细），最后断言两次完全一致：走查里的写操作（矩阵 +1 再还原、导出回灌、记一笔再删）**净效应必须是零**。"界面数字等于接口数字"证明不了这一点——数字一起被改了它也会全绿，所以这条前后对比是导出回灌幂等的兜底防线。

接口现在都要登录，两个回归脚本会自己处理：实例上还没有账号时用默认凭证 `admin / admin123456` 建一个；已经有账号时用环境变量传入。

```bash
WALKTHROUGH_BASE=http://127.0.0.1:8012 \
WALKTHROUGH_USER=admin WALKTHROUGH_PASSWORD=你的密码 \
.venv\Scripts\python backend\scripts\walkthrough.py
```

## 金额口径

原价（预算）= Σ数量 × 单价，含分组覆盖价；日常价 = Σ数量 × 日常单价（**不含**覆盖价，某个分组单独定价不影响日常价口径）。

已付 = Σ采购记录金额。未付 = 剩余数量 × 单价 —— 是「还没买的那部分按原价要花多少」，**不是**「原价 − 已付」：一笔付款可能远高于或远低于对应数量的原价，相减会得出负数。

两个口径各自都能拆成三段，且严格相等（到分）：

```
已付 + 实际优惠 + 未付         = 原价合计
已付 + 日常价优惠 + 日常价未付 = 日常价合计
```

- **日常价未付** = 剩余数量 × 日常单价
- **实际优惠** = 原价合计 − 已付 − 未付，即已买部分相对原价省下的钱
- **日常价优惠** = 日常价合计 − 已付 − 日常价未付，即已买部分相对日常价省下的钱

两个优惠是**残差**而非独立计算，所以有分组覆盖价、买超、部分付款时等式都照样成立。实付价高于原价或日常价时它们为**负数**（比原价/日常价还多花了钱），界面按负号加警示色显示，不做夹断——夹成 0 会让等式对不上。

## 技术要点

- **采购状态**由采购记录推导：未买 / 部分已买 / 已买完；无数量需求时显示"无需采购"
- **表格撑满容器**：面板 flex 布局 + 独立滚动视口 + `ResizeObserver` 同步 `<el-table :height>`，表头固定、只有内容区滚动
- **玻璃卡片间隙**：阴影用负 spread 只向下投射，避免相邻卡片阴影在窄缝里叠加成灰条
- **多清单怎么隔离**：接口路径和字段名一律没动（老版安卓客户端照常能用），隔离靠请求上带的一个清单标识 —— 网页和安卓走 `X-List-Id` 请求头，导出这类 `<a href>` 直接导航的走 `?list_id=` 参数，两者都没有就落到第一份清单。不属于当前清单的 id 一律按"不存在"处理（404），不泄露别的清单里有什么
- **多清单的数据模型**：`lists` 表 + `items/rooms/categories` 上的 `list_id`；采购记录和分配不直接挂清单，它们跟着物料走。分类的"同名"只在清单内唯一（`(list_id, name)`），不同清单可以各有一份「照明」
- **矩阵的「已买齐」只在能确定时标绿**：付款记录不绑定分组，"先买的是哪一间"系统无从知晓。所以只在这两种情况下标：这条物料**只分给一个分组**（不存在先后）、或者**整条已经全部买完**（每一行都满，是事实）。多分组只买了一部分时一个都不标——按分配顺序硬抵会让人以为先做的那间已经买齐。进度交给物料行上的「实付 3/7」表达
- **乐观并发**：每条物料带一个 `rev`，整条保存时如果对不上（说明这期间别处也改过）返回 409，由用户决定覆盖还是先看最新的，免得把已经导进去的付款悄悄抹掉
- **安卓端口径一致**：客户端把 `compute.py` 的公式复刻了一份用于表单实时预览，但保存后的权威结果始终以后端返回为准；任何写操作成功后只发一个版本号，各页面据此重新拉数据
- **一套 token 两种携带方式**：网页用 httpOnly Cookie（「设置」里那两个导出下载是纯 `<a href>` 导航，没法加请求头，用 Cookie 才能自动带上，也顺带挡住脚本偷凭证）；安卓用 `Authorization: Bearer`。后端两种都认，`require_user` 挂在路由上，登录接口本身不挂
- **无状态会话**：token 里带了密码指纹，所以改密码会自动让所有旧 token 失效，不需要额外维护会话表。签名密钥只依赖标准库 `hmac`，密码哈希用 `hashlib.pbkdf2_hmac`，运行镜像不用装 bcrypt/passlib
- **改密码/被登出是同一个机制**：安卓端任何请求撞上 401 就清掉本地 token，顶层路由监听到登录态变化自动切回登录页，各页面不用各自处理
